**T7**
- `/api/status` 不再呼叫 `getSnapshot()`（會打 `listSessions()` 磁碟 I/O），改走新的輕量 `getPublicStatus()`，並加 120/分 rate limit。此路由在 cookie 驗證之前，只要有隧道 URL 就打得到。
- 配對失敗計數分離：**錯誤的 pairingSecret 不再計入鎖定**。原本任何人丟 5 次垃圾 POST 就能把合法手機鎖在門外；secret 是 192-bit，暴力破解本來就靠熵＋10/分限流擋，不需要靠鎖定。PIN 錯誤維持 5 次鎖定。
- `parseCookie` 的 `decodeURIComponent` 包 try/catch（`%E0%A4%A` 這種非法編碼原本會 500，現在視同未登入 → 401）。
- `handleInterject`／`handleQueue` 套用與 prompt 相同的 `REMOTE_PROMPT_MAX_CHARS`；`/api/cancel`、`/api/queue` 補上 20/分 rate limit。

**T8**：`handleStatic` 改用新的 `resolveWebRootPath()`——`path.resolve` 後用 `path.relative` 確認在 webRoot 內，並擋掉 Windows 磁碟機代號、UNC、裝置路徑、ADS、NUL、無法解碼的路徑。新增 `tests/remote-static-path.test.ts`（5 個 case）。原本的安全是**意外達成的**（靠 `path.join` 語意 + WHATWG URL 正規化兩個沒人寫下來的行為），現在寫死。

**T9**：`grok:config`（`setConfigOption`）與 `preview:stat`（`previewStat`）從 preload / bridge 型別 / main handler 移除。`previewStat` **函式本身保留**——`previewRegister` 與 `previewReadText` 內部仍在用，死掉的只有 IPC 暴露面。acp-client 的 `setConfigOption` 一併移除（標準 `session/set_config_option` 在此 CLI 回 Method not found）。

**T10（重要：結論與原報告不同）**
`renderSessionRow` 抽成 memo 化的 `SessionRow` 元件，handler 走 ref 保持 identity 穩定。但**實測顯示這不是瓶頸**：

| 量測 | 數字 |
|---|---|
| 側欄規模 | 55 列 / 220 顆按鈕 / 1345 個節點 |
| 每次按鍵的 frame 成本（memo **開**） | median 11.2ms、p95 15.4ms |
| 每次按鍵的 frame 成本（memo **關**，A/B 對照） | median 11.1ms、p95 14.3ms |
| 40 次按鍵中的 long task（>50ms） | **0** |

**memo 沒有帶來可測量的改善**，p95 仍在 16ms frame budget 內。原報告 D4 說「每次串流事件都會重跑 216 顆按鈕的 render」描述屬實，但**成本可以忽略**。
→ **不做虛擬化**。理由：grouped 列表虛擬化會動到捲動位置保存、刪除的收合動畫、多選 checkbox、鍵盤導覽，風險遠大於 0ms 的收益。
→ 保留 memo 抽出：對結構可讀性有幫助、執行期零成本、對話數成長時是保險。**但這是保險，不是已量測到的修復**——若你偏好最小 diff 可以回退。

（附註：`Ctrl+B` 收合側欄只是視覺收合，rows 不會卸載，所以那組對照只隔離出 paint/layout，p95 差約 2.7ms。）

**額外抓到並修掉的真缺陷（T4 迴歸驗證時發現）**
書籤跳轉在**長對話**上會落錯位置：Virtuoso 對高度沒量過的項目 `scrollToIndex` 只落到大概位置。實測跳第一則指令時停在 11850（該停 0），頂端顯示的是 Reasoning 而不是那則指令。修法：`JUMP_SETTLE_DELAYS_MS = [220, 520]`，在列表 settle 後補跳。修後實測 12591 → **0**，頂端正是該則指令。

### probe 本身的兩個修正（飄動的閘比沒有閘更糟）
1. `.transcript` 底下有**兩個**元素回報 `scrollHeight > clientHeight`，其中一個永遠 `scrollTop=0`。原本的 `.find()` 會挑到不會動的那個，導致假失敗。改成取 scrollTop 最大者。
2. 斷言從「scrollTop 必須變小」改成「被點選的那則指令跳完後在視窗內可見」——短對話裡指令本來就在畫面上，正確的跳轉就是 no-op，舊斷言等於要求它出錯。
3. `/compact` 在極小 context 可能完全不發事件（AGENTS.md 已記錄的 CLI 行為），該情況改報 INCONCLUSIVE 而非 FAIL。
